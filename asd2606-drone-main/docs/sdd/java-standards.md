# Java 项目开发规范

> 本文件是 SDD 流程在**编码层面**的细则，配合 [`README.md`](./README.md) 使用。
> 项目宪法（`constitution.md`）可以**加严**本文件，**不得放宽**。

## 0. 基线、分级与冲突处理

- **基线**：《阿里巴巴 Java 开发手册》【强制】条目为**底线**（下文不再逐条抄录原文，
  只列落地时最容易违反和被忽略的条目）。格式细则参考 Google Java Style。
- **分级**：【强制】必须做到，违反即视为不合格；【推荐】应当做到，不做要说明理由；
  【参考】供选型参考。
- **【强制】冲突处理**：本文件与基线冲突时以本文件为准（本文件是加严后的结论）；
  本文件未覆盖的，回到基线手册。
- 【强制】基线手册的全文不在仓库内，但团队必须能访问到；评审时以手册条文编号引用。

## 1. 工程结构与依赖

- 【强制】统一用 Maven，`groupId` 与组织一致，`artifactId` 用 kebab-case。
- 【强制】Spring Boot 项目一律继承 `spring-boot-starter-parent`，**显式指定版本**，
  禁止用 `LATEST`/`RELEASE`/版本区间。
- 【强制】依赖版本统一在 `<properties>` 里声明，禁止在多处散落版本号。
- 【强制】包结构按**业务模块**划分（`order`、`payment`），模块内部再分层；
  禁止按技术分层做顶层包（在 `controller/`、`service/` 下堆全公司所有类）。
- 【强制】依赖方向单向：`web → service → dao`。反向依赖一律禁止
  （dao 不得引用 service，service 不得引用 controller 的类）。
- 【推荐】多模块时用 `dependencyManagement` 统一版本，模块间不重复声明版本。
- 【强制】提交前 `mvn -q compile` 与测试必须通过；不得提交编译不过的代码。

## 2. 命名

- 【强制】类/接口 `UpperCamelCase`；方法、参数、成员变量 `lowerCamelCase`；
  常量 `UPPER_SNAKE_CASE`。
- 【强制】禁止拼音与英文混用，禁止中文命名（领域术语无对应英文时，
  在 `constitution.md` 里给出统一译名表）。
- 【强制】禁止用下划线或美元符号开头/结尾命名。
- 【强制】布尔类型字段/方法**不加 `is` 前缀**（`success` 而非 `isSuccess`），
  避免序列化框架把它当成 `<isSuccess>` 属性。
- 【强制】禁止在 POJO 中同时出现属性 `xxx` 的 `getXxx()` 与 `isXxx()` 两种读方法。
- 【强制】领域名词统一：同一个概念在全项目只能有一个词（`user` / `member` 不得混用）。
- 【推荐】测试类名 `被测试类名 + Test`；验收测试按需求 ID 命名，
  如 `ReqTask0012AcceptanceTest`。

## 3. 分层与对象模型

| 层 | 职责 | 禁止 |
|---|---|---|
| Controller | 接收请求、参数校验、编排调用、组装响应 | 写业务逻辑、直接调 dao、拼 SQL |
| Service | 业务规则、事务边界、编排 | 感知 HTTP（不得出现 `HttpServletRequest`/`ResponseEntity`） |
| DAO / Mapper | 数据存取 | 写业务判断 |
| 外部客户端 | 第三方调用、协议转换 | 泄露第三方模型到上层（须转成自己的模型） |

- 【强制】对象职责不可混用：`DTO`（跨层传参）、`VO`（对外返回）、`Entity/PO`（对应表）、
  `BO`（领域内部）。**禁止把 Entity 直接当接口出参返回**。
- 【强制】`Controller` 只接受 `DTO` 入参、只返回 `VO`（或统一响应体包裹的 `VO`）。
- 【强制】**对外接口必须做参数校验**（`@Valid` + 注解，或显式判断），
  校验失败返回明确错误码，不要靠下游报 NPE 才发现。
- 【强制】事务注解加在 Service 层方法上，且方法必须是 `public`（否则注解不生效）。
- 【推荐】事务方法内**不要**做远程调用、发消息、发邮件等耗时且不可回滚的操作；
  必须先提交事务再发消息，或用本地消息表保证最终一致。
- 【强制】禁止大事务：一次事务不要处理超过 500 条记录的批量写。

## 4. 接口契约

- 【强制】**统一响应体**，全项目一致，业务失败也返回 HTTP 200 + 业务码
  （或全项目统一用 HTTP 状态码——二选一并在 `constitution.md` 里写死，不允许两种混用）。
- 【强制】接口必须有**错误码表**：错误码唯一、含义稳定、不得复用。
  错误码一旦发布不得改变含义（只能新增）。
- 【强制】分页请求/响应结构统一（页码、每页条数、总数、列表），不得每个接口一套。
- 【强制】列表接口必须有**分页上限**（如每页最大 200 条），防止被一次拉全表。
- 【强制】对外接口用 HTTP 动词表达语义；**查询禁止用 POST**。
- 【推荐】写接口设计为**幂等**（用业务唯一键或幂等 token），
  并在文档里标明该接口是否幂等。
- 【强制】接口变更必须更新接口文档（OpenAPI 或 `plans/` 中的接口清单），
  并在 `plans/` 里给出兼容性结论。
- 【强制】入参长度、范围、格式在服务端校验；不得信任前端校验。

## 5. 异常与日志

- 【强制】业务异常用**自定义异常 + 错误码**，禁止用异常做流程控制。
- 【强制】**禁止吞异常**（`catch` 后什么都不做）。捕获就必须处理：记录、转换或重新抛出。
- 【强制】`finally` 中**不得** `return`；资源释放优先用 try-with-resources。
- 【强制】不得捕获 `Throwable` / `Error`；不得捕获 `Exception` 后一律包装成同一异常，
  要区分稳定代码与非稳定代码。
- 【强制】日志用 SLF4J，**禁止** `System.out` / `System.err` / `e.printStackTrace()`。
- 【强制】日志**必须用占位符** `log.info("id={}", id)`，禁止字符串拼接
  （拼接会在日志级别关闭时白白付出性能代价）。
- 【强制】**禁止打印敏感信息**：密码、令牌、身份证、手机号（需脱敏）、**任何密钥**。
  请求头里的 `Authorization` 属于此列。
- 【强制】记日志要带**定位信息**（业务 ID、用户 ID、traceId），
  否则出事时日志等于没有。
- 【推荐】异常日志记 `error` 并带堆栈，业务拒绝记 `warn`，正常流程记 `info`/`debug`。
- 【推荐】跨服务调用传入 traceId，便于串联链路。
- 【推荐】外部调用（模型、第三方接口）**前后各留一条**，且前后能对上同一个关联标识 ——
  否则「进去了没出来」这种情况无从判断。

> **本项目的日志读者定位是初级工程师**（与第 13 节的注释同一定位）。
> 由此派生下面四条，它们不是锦上添花：日志写得让人读不懂，等于没写。

- 【强制】**关键流程节点必须有一进一出。** 一次请求从进到出，日志应当能读出一条完整链路：
  接口入口 / 业务编排的每一步 / 外部调用前后 / 状态变更前后 / 接口出口。
  只留下「进来了、出去了」两条，出事时定位不到卡在哪一步。
- 【强制】一条日志要**自解释它正在干什么**，而不是只打一个值。
  反例：`log.debug("{}", key)`；
  正例：`log.info("开始组装上下文：userId={}，conversationId={}")`。
- 【强制】**异步与后台动作的日志必须标明它是异步发生的**（由回调线程、定时任务触发等）。
  否则「日志里没有这条」和「这件事没发生」根本区分不了 —— 本项目已经踩过这个坑：
  会话归档是异步的，不标明就推不出「是没归档，还是还没轮到它」。
- 【推荐】失败日志除原因外，还要写清**接下来会怎么处理**：会重试 / 会丢弃 / 返回给用户什么。
  只写「失败了」的日志，读的人还得回头翻代码才知道后果。

## 6. 数据访问与迁移

- 【强制】禁止 `SELECT *`；查询必须显式列出字段。
- 【强制】禁止在循环里访问数据库（N+1）。批量场景用批量接口或一次查全再内存拼装。
- 【强制】SQL 参数用占位符（`#{}` / 预编译），**禁止字符串拼接 SQL**（SQL 注入）。
- 【强制】统计行数用 `count(*)`。
- 【强制】表必备三字段：`id`、`create_time`、`update_time`；表名、字段名用
  `lower_snake_case`；不得使用数据库保留字。
- 【强制】索引命名：唯一索引 `uk_<字段>`、普通索引 `idx_<字段>`；
  关联查询字段、`where` 常用字段必须建索引。
- 【强制】**不使用外键与级联**，一致性在应用层保证。
- 【强制】禁止物理删除业务数据（用逻辑删除或归档）；不得使用存储过程。
- 【强制】**表结构变更必须通过新增迁移脚本**，不得直接改老脚本。
  迁移脚本按顺序执行、可重复执行（幂等），文件头部写明前提与执行顺序。
- 【强制】迁移脚本必须给出**回滚方案**（或明确说明为何不可回滚）。
- 【推荐】大表加字段、加索引评估锁表影响，给出执行窗口。

## 7. 配置与密钥

- 【强制】**禁止硬编码**环境地址、账号、密钥、开关；一律走配置或环境变量。
- 【强制】配置文件里的密钥写成占位（`${DB_PASSWORD:}`），**真实值不得进仓库**。
- 【强制】提交前自检：`git diff` 里不得出现密钥、令牌、私钥、
  生产地址、真实用户数据。
- 【强制】本地开发/测试/生产配置分离；不得为了让本地跑通而改生产配置。
- 【推荐】配置项在 `constitution.md` 或项目 README 里集中列出用途，
  避免「有个配置没人知道干什么」。

## 8. 安全

- 【强制】所有非公开接口**必须鉴权**，且鉴权在统一入口做（拦截器/过滤器），
  不允许每个接口各写一遍。
- 【强制】**越权防护**：查询/修改必须校验数据归属（`资源ID` 是否属于当前用户/租户），
  不能只依赖前端不传别的 ID。
- 【强制】权限判断放服务端；前端隐藏按钮只是体验优化，不构成安全边界。
- 【强制】对外输入一律视为不可信：长度、类型、范围、格式、文件类型与大小都要校验。
- 【强制】文件上传限制类型白名单与大小上限，存储路径不得由用户输入直接拼接
  （防路径穿越）。
- 【强制】敏感数据落库加密或脱敏；日志与接口返回都要脱敏。
- 【推荐】引入依赖漏洞扫描（如 `dependency-check`）并纳入 CI。
- 【推荐】对外暴露的内部接口必须走独立鉴权（共享密钥/内网隔离），不得与用户接口混用同一套凭据。

## 9. 测试

- 【强制】单元测试遵循 AIR：自动运行（Automatic）、互不依赖（Independent）、可重复（Repeatable）。
- 【强制】测试**不得依赖外部环境**（真数据库、真 MQ、真第三方）——
  用内存实现或桩件替代；确需真实依赖的归入集成测试并单独标记。
- 【强制】测试命名表达「被测行为 + 预期结果」，禁止 `test1`/`testMethod` 这种名字。
- 【强制】断言必须具体（断言值、异常类型与消息），禁止只断言「不抛异常」。
- 【强制】**验收条件必须逐条对应测试**：`specs/` 里每一条验收条件，
  在测试里都能找到对应用例；做不到就在 `plans/` 里说明原因。
- 【强制】覆盖率门槛：核心业务模块行覆盖 **≥ 80%**，全项目 **≥ 60%**；
  覆盖率不得靠排除文件来达标。
- 【推荐】纯工具类/映射转换类可用参数化测试覆盖边界。
- 【强制】修 Bug 必须先写一个**能复现该 Bug 的失败测试**，再修。

## 10. 静态检查与构建

- 【强制】接入代码格式与静态检查（如 Spotless/Checkstyle/PMD、前端 ESLint+Prettier），
  并纳入构建；**不允许「本地不跑、提交了再说」**。
- 【强制】构建脚本可重复执行，不依赖本地已有产物（`clean` 后能一次跑通）。
- 【强制】CI 至少跑：编译、静态检查、单元测试；任一失败即视为不可合并。
- 【推荐】格式化规则随仓库提交（配置文件进仓库），不靠个人 IDE 设置。

## 11. Git 与交付

- 【强制】提交信息采用 **Conventional Commits**：
  `type(scope): subject`，`type` 取 `feat|fix|refactor|perf|test|docs|chore|build|ci`。
- 【强制】提交信息**必须带需求 ID**，写在正文里（如 `Refs: REQ-TASK-0012`），
  使「提交 → 需求」可追溯。
- 【强制】一个提交只做一件事；格式化等无行为改动必须**单独提交**，
  不得混进功能提交（否则 diff 无法评审）。
- 【强制】禁止提交：`target/`、`node_modules/`、构建产物、IDE 配置、
  本地数据、密钥、大文件。
- 【强制】分支命名：`feat/<需求ID>-<短名>`、`fix/<需求ID>-<短名>`。
  主干分支受保护，禁止直接推送。
- 【强制】合并前必须通过代码评审；评审人按 `constitution.md` 与
  `java-standards.md` 逐条对照，不接受「看着没问题」。
- 【推荐】版本号遵循语义化版本；破坏性变更必须在 `plans/` 里写明迁移步骤。

## 12. 文档

- 【强制】设计文档与代码**同仓库、同分支**，随代码一起评审和回滚。
- 【强制】架构决策记 ADR（`docs/sdd/decisions/`）：一决策一文件，
  写清背景、可选方案、结论、后果。**结论要写「不选什么、为什么」**。
- 【强制】对外接口文档从代码生成（OpenAPI）或与代码同源，禁止手工维护两份。
- 【强制】规范与实现不一致时，**当场修掉**，不允许挂账。
- 【推荐】注释**既讲「为什么」，也讲「怎么执行」**（流程、步骤、边界）。细则见第 13 节 ——
  只讲 why 对初级工程师不够：他可能连这段代码在干什么都还没看懂。

## 13. 注释规范

> **读者定位：初级工程师。** 日志与注释都按这个前提写。
> 目标不是「老手扫一眼就懂」——他本来就懂、不需要注释；而是**让刚接手的人能顺着读下来**，
> 看懂代码**怎么执行**、处在整条链路的哪一步。

- 【强制】**类/接口的头注释**写清三件事：这个类负责什么、在整条链路中处于哪一步、
  **它不负责什么**。边界最容易被新人误解 ——「这个类为什么没做 X」和「X 由谁做」要能读到。
- 【强制】**方法注释**写清：每个入参的含义、返回值的含义、会抛出什么，
  以及**顺带做了什么**（副作用：写库、写文件、发消息、改缓存）。
  只写「此方法用于处理…」等于没写。
- 【强制】**关键流程按步骤编号注释**（第一步 / 第二步…），让读者能对照着走完整条链路。
  流程一长，没有编号的注释就只是一团散文。
- 【强制】**反直觉之处必须写清「为什么这么做」和「不这么做会怎样」。**
  这是注释里最值钱的部分：代码能说明「做了什么」，说明不了「为什么不那样做」。
- 【强制】**复杂表达式、正则、下标与边界计算必须有注释说明含义。**
  形如 `(?<!\d)(\d{6})\d{8}([\dXx]{4})(?!\d)` 的写法，不解释没人看得懂。
- 【强制】注释用中文。**代码自己能说清楚的部分不要用注释复述** ——
  先用命名把话说清楚，注释只补命名说不出来的东西。
- 【强制】注释**只写当下的事实**。禁止出现「今天改成 X」「原来写的是 Y」这类会过期的话；
  变更过程放提交信息或 ADR。**注释与代码不同步时以代码为准、当场改注释。**
- 【推荐】每段注释按「为什么这么做 / 怎么执行 / 坑在哪」三层来想；
  不必每段都齐全，但缺哪一层就补哪一层。

### 反例与正例（同一段代码）

```java
// 反例：只复述了代码在做什么，等于没写
// 遍历 messages，取最后 20 条
List<ChatMessage> tail = allowed.subList(Math.max(0, allowed.size() - 20), allowed.size());

// 正例：交代在整条链路里的位置 + 为什么这么算 + 不这么做会怎样
// 第四步：截断会话内上下文。只取最近 20 条有两个原因：
//   一是模型有上下文窗口上限，二是更长也帮不上忙（远期对话对当前这轮几乎没有信息量）。
// 注意取的是「后 20 条」而不是「前 20 条」——取前面会把刚聊的内容丢掉，
// 模型会表现得像没听见你上一句。
List<ChatMessage> tail = allowed.subList(Math.max(0, allowed.size() - SESSION_MESSAGE_LIMIT), allowed.size());
```
