## 1. 方案概述

三件事都落在 `ToolCallingService` 的循环**内部**，**不动** ReAct 骨架（跨轮仍串行）：

1. **受控重试**：某次工具**失败**时，把失败信息当作普通「工具结果」回填，让模型再决断；
   用一个**重试计数**保证「最多再试 1 次」，到顶即收尾。
2. **分级压缩**：工具回填内容先做**结构化裁剪**（去 URL / 去重复行 / 只留前 N 条）；
   仍超长再**调一次模型摘要**。两者都有长度阈值，正常内容**不触发**任何额外调用。
3. **显式预算**：把「只有一个轮数上限」扩展为 **步数 / 单次回填长度 / 结果总量** 三个预算，
   超预算**有序收尾**（返回已有内容并说明），而不是报错。

全部由 `agent.tool.optimize-enabled` 一键开关；关掉即回到现状。

```yaml

    optimize-enabled: true      # 本需求的三个优化总开关；false 即回到现状
```

## 5. 关键设计决策

| 决策点 | 备选方案 | 结论 | 理由 |
|---|---|---|---|
| 压缩方式 | ①纯截断（现状）②只结构化裁剪 ③只模型摘要 ④**分级** | **④** | 需求方定；正常内容不花额外调用，超长才升级到摘要 |
| 重试触发 | ①失败或无结果都重试 ②**仅失败** | **②** | 「无结果」多半是关键词本身没命中，重试是白花钱 |
| 重试实现 | ①编排层再执行一次工具 ②**把失败信息回填，交给模型决断** | **②** | 让模型自己决定「换参数 / 换工具 / 放弃」，比机械重试更聪明；计数仍由编排层保证上限 |
| 预算落点 | ①只加步数 ②**步数 + 单次长度 + 总量** | **②** | 只限步数挡不住「一步塞进超长结果」 |
| 超预算行为 | ①报错 ②**有序收尾** | **②** | 与 AC-4 一致：用户该拿到「已有的部分 + 说明」，不是 500 |
| 与 0005 的关系 | ①各写一套预算/日志 ②**共用同一配置与日志口径** | **②** | 避免两个需求各加一个「步数」导致语义打架 |

## 7. 风险与回滚

| 风险 | 触发条件 | 影响 | 应对 |
|---|---|---|---|
| 摘要多花一次调用 | 结果频繁超长 | 成本↑、延迟↑ | 分级：先裁剪，**仍超长才**摘要；阈值可配 |
| 重试放大成本 | 工具持续失败 | 多花额度 | 上限 1 次，到顶即收尾 |
| 裁剪丢关键信息 | 结构化裁剪太激进 | 答复质量↓ | 保留标题/数值行，只去 URL 与重复；摘要兜底 |
| 与 0005 配置打架 | 两需求各加预算项 | 语义混乱 | 本需求**统一**在 `agent.tool.*` 下并在部署文档对齐 |

- 上线方式：**配置**（`optimize-enabled`，默认开）
- 回滚步骤：`optimize-enabled=false` 后重启；**无需数据修复**
- 回滚后数据是否需要修复：**不需要**
