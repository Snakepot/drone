# 技术方案 — REQ-AGENT-0003 会话与长期记忆

- **需求 ID**：`REQ-AGENT-0003`
- **作者 / 日期**：AI / 2026-10-12
- **评审人 / 评审日期**：项目负责人 / 2026-10-12（**评审通过**）
- **输入**：[`../specs/REQ-AGENT-0003-会话与长期记忆.md`](../specs/REQ-AGENT-0003-会话与长期记忆.md)、[`../decisions/ADR-0003`](../decisions/ADR-0003-引入记忆与服务端有状态.md)

## 1. 方案概述

`drone-agent` 新增一个记忆子系统（包 `cn.tedu.droneagent.memory`），分三层：

- **会话存储（内存）**：Caffeine `Cache<SessionKey, Session>`，按 `userId + conversationId` 存消息，
  负责容量上限、空闲过期、以及**过期/淘汰时的落盘**。
- **长期存储（文件）**：`<root>/<userId>/` 下按日期分片，配一份**按用户隔离的索引** `memory.md`。
- **脱敏**：落盘前对消息内容做规则替换。

对话契约随之改为 `conversationId + message`：客户端不再回传历史，服务端自己组装上下文。

## 2. 影响面

| 维度 | 影响 | 说明 |
|---|---|---|
| 接口 | **修改（破坏性）+ 新增** | `/chat`、`/chat/stream` 入参变更；新增会话列表与删除 |
| 数据模型 | 无数据库变更 | 长期记忆落文件，不进 MySQL |
| 兼容性 | **不兼容** | 第二次破坏契约（第一次见 `REQ-AGENT-0002`）。唯一调用方在仓库内 |
| 性能 | 有影响 | 每次对话多一次内存读 + 落盘（异步/过期时）；启动**零文件读取** |
| 其他服务 | 无 | 不涉及 `drone-server` |
| 前端 | `drone-web` 需改 | 会话 id 管理、新建会话按钮、会话列表、删除入口 |
| 部署 | **需挂卷** | 否则容器重建即丢长期记忆（规格「约束与依赖」已列） |

## 3. 接口清单

| 方法 | 路径 | 入参 | 出参 | 鉴权 | 幂等 |
|---|---|---|---|---|---|
| POST | `/chat` | `{conversationId, message}` | `JsonResult<{reply}>` | `agent:chat` | 否 |
| POST | `/chat/stream` | `{conversationId, message}` | `text/event-stream` | `agent:chat` | 否 |
| GET | `/chat/sessions` | — | `JsonResult<[{conversationId, title, startedAt, messageCount}]>` | `agent:chat` | 是 |
| DELETE | `/chat/sessions/{conversationId}` | 路径参数 | `JsonResult<Void>` | `agent:chat` | 是 |

**契约变更说明**：`messages` 字段**移除**。服务端不再接受客户端提交的历史——
这是本需求的核心目的（消除客户端伪造轮次的可能）。
不保留旧字段做兼容：宪法第 1 节禁止为兼容而留死字段，且唯一调用方在本仓库内可同步改。

**越权**：`conversationId` 由前端生成的 UUID，但**归属以服务端记录的 userId 为准**。
请求里的 `userId` 一律取自 Token，绝不接受客户端传入。

**id 字符集约束（T-5）**：`conversationId` 会被**原样写进记忆文件的格式**里
——索引行是 `conv=<id> | ...`，正文段头同理。id 里带 `|` 或换行，一行会被多切一段、
或凭空多出一行，把别人的记录顶歪。已在 `SessionKey` 构造处限定为
`[A-Za-z0-9_-]{1,64}`（唯一入口，比在每个写文件的地方各挡一次可靠）。

## 4. 存储布局

```
<root>/                                  # agent.memory.root，默认 ./data/agent-memory
├── audit.log                            # 删除审计，一行一条 JSON，append-only
└── <userId>/
    ├── memory.md                         # 该用户的索引（按用户隔离）
    ├── memory-2026-10-12.md              # 正文，按日期分片
    └── memory-2026-10-12-2.md            # 单文件超 2MB 后滚动
```

**索引行格式**（一行一条会话，**不含正文**）：

```
- 2026-10-12 14:32 | conv=8f3c4d21 | 12 | 电池低温报警 | memory-2026-10-12.md
  ↑日期时间        ↑会话id         ↑条数 ↑首句(截断)   ↑所在文件
```

**这样设计的直接收益**：会话列表**只解析索引**即可返回，不读任何正文文件；
`title` 取首句也无需读正文。

**删除时必须同时删索引条目**（T-4 已实现）。少了这一步，正文清掉了、索引里还留着，
会话列表上就会出现一个**指向已删内容的幽灵条目**——点进去什么都没有。

**两处刻意的取舍**（T-4 落地时明确）：

- **时间只精确到分钟**。索引是给人扫的，秒没有意义；代价是同一分钟内的两个会话时间相同，
  排序只能靠写入顺序。已用测试把这一点钉住，免得有人以为秒被保留了。
- **追加不做原子替换**。追加崩溃最多留下一行残缺内容，读取时跳过并告警，不影响前面的记录；
  为它每次重写整个文件不划算。只有删除（过滤后整体重写）才走原子替换。

**T-5 落地时补记的两点**
- **正文的追加同样不原子**（与索引一致）。崩溃最多在文件末尾留半截会话段，
  为它每次重写整个 2MB 文件不划算；删除走原子替换。**单个会话段大于文件上限时
  仍会被写出**——一段会话不能拆开，这是上限的例外。
- **原子重写的实现抽成了 `TextFiles`**。索引与正文两处都要它，各写一份迟早一边修一边漏。
  （T-4 时先写在 `MemoryIndex` 内部，T-5 出现第二个使用者后抽出来的。）
- **正文用转义而不是缩进续行**处理多行内容。缩进好看，但正文里完全可能出现
  以 `user: ` 开头的行（模型解释对话格式、用户粘日志都会），按行首标记解析会把一段话切成两截。
  转义后一条消息严格占一行，解析不依赖内容长什么样；代价是读文件时多行显示为 `\n`。

**T-6 落地时补记的三点**

- **重试必须按「本轮快照」做，不能边取边放。** 失败项若在轮内立刻放回队尾，
  同一轮会立刻再取到它，于是一个失败项在一轮里被重试几十次——
  等于持续猛敲一个已经出故障的磁盘。改为一次性取出本轮要处理的部分，
  逐个尝试，失败的再入队等下一轮（实现时先写错了，测试日志暴露后修正）。
- **索引写入失败时，重试只补索引、不重写正文。** 否则同一文件里会出现两个同名会话段。
  待重试项因此要记住「正文已写、文件名是它」。
- **停机刷盘是同步的**，不走异步执行器——停机正是最不该依赖「等队列把活干完」的时刻。

**T-7 落地时补记的三点**

- **同一个会话会被归档多次，读的时候必须取最新一段。**
  会话被淘汰时归档一次；用户回来接着聊、再被淘汰，就又追加一段。
  而原来的读取实现取的是**第一段**——恢复出来的是上一次归档时的旧内容，**越用越倒退**。
  已改为「取最后一段」，并加了回归用例。
- **索引里同一个会话也会累积多条**，原因是同一个：每次归档都追加一行。
  已改为在 `MemoryIndex.list` 读的时候收敛成一条（最新的那条），
  而不是让每个调用方各自去重——否则会话列表会重复、懒加载会取错文件。
- **恢复出来的内容是脱敏后的**：正文落盘前已脱敏，所以读回来的是 `138****8000`。
  这是「落盘必须脱敏」与「能从盘上恢复」叠加的必然结果，**不是缺陷**；
  但意味着**跨重启的长对话里，敏感字段的信息已不可逆地损失**。
  这条已写进 `LongTermSessionLoader` 的类注释，免得日后被当成 bug 排查。

**T-8 落地时补记的三点**

- **「轮」的定义此前没写死，本次定为「一问一答 = 2 条消息」。**
  原方案只写了「最近 10 轮」，没说一轮是多少条；按 2 条实现，因此轮数预算实际是 20 条消息。
  之所以要写清，是因为它直接决定注入量——理解成 1 条就等于把预算砍半。
- **会话内那部分只按条数封顶（20 条），不另设字符上限。**
  长期记忆才受「轮数 + 字符」双约束。理由：会话内是刚聊过的内容，
  再砍一刀会让对话忽然断片；而长期记忆是背景补充，砍掉最早的没有体感损失。
- **单条内容大于整个字符预算时，长期记忆一条都注入不进来。**
  实现上不做「把一条消息切断」的事（截断半句话比不给更糟），
  于是遇到超长单条就整体放弃长期记忆。这是已知边界，不是缺陷——
  它只影响长期记忆，会话内上下文不受影响。

**T-9 ~ T-13 落地时补记的六点（对话接口与会话管理）**

- **T-9 与 T-10 无法分开实施。** 任务表把它们拆成两条，但改 `ChatRequest` 会立刻打断
  `ChatController` 的编译，留不出「可编译的中间状态」。两条合并实施，任务表已注明。
- **响应里的 `lastActiveAt` 去掉了。** 原接口清单列了它，但索引里没这个字段；
  要加就得改索引的行格式，而**格式一改，已有的索引文件会解析失败**——
  那等于把历史会话从列表里抹掉。需要它时应作为独立改动，连带做一次索引迁移。
- **会话列表不含「还没归档过」的会话。** 新开的会话要等被淘汰或停机刷盘后才进索引，
  在那之前列表里看不到它。这是当前已知边界，**不是越权问题**（列表里出现的永远只有自己的）。
  要补就得把内存中的会话一并并入列表，属独立改动——本期按任务原意的「只读索引」实现。
- **同会话正忙返回 409，不是 400 也不是 500。** 这不是请求写错了，而是**时机不对、重发就行**；
  前端据此可以提示「上一条还在处理」，而不是去改请求参数。
- **`ChatService` 不再校验历史。** 校验整体移到组装环节（`ContextAssembler`）——
  在那里才拦得住源头，留在模型调用前既拦不住也已多余。因此
  `normalizeHistory` 与其 8 个单测一并删除，`ChatServiceTest` 改为只测
  **请求体形状**（系统提示词永远第一条、上下文顺序不变）。`REQ-AGENT-0002` 那批
  验收条件的覆盖随之转到 `ContextAssemblerTest`。
- **装配踩到一个坑：一个类有两个构造方法时 Spring 会挑不出来。**
  `ConversationService` 多了一个「短超时」构造供测试用，Spring 直接报
  `No default constructor found`。需在主的那个上标 `@Autowired` 指明。
  这个错是 `MemoryPropertiesTest`（会启动上下文的那个测试）抓到的——
  **纯单测全绿也拦不住装配问题**，上下文测试不能省。

**T-14 ~ T-16 落地时补记的四点（前端）**

- **会话 id 的生命周期抽成了 composable**（`useConversationId`），没有写在面板组件里。
  理由是可测性：写在组件里就得引入 `happy-dom` + `@vue/test-utils` 才能测，
  而那是新增依赖、要评审。抽出来之后它就是纯 JS + localStorage，**node 环境直接能测**。
- **刷新页面的行为按任务的约定实现**：id 记入 localStorage 所以会话不变、服务端上下文连续；
  但**面板不会回填历史消息**——接口里没有「取某会话聊天记录」这一条。
  于是刷新后面板是空的、助手其实还记得。这不是 bug，`useConversationId` 暴露了 `restored`
  标记，面板据此显示一句提示，免得用户误以为助手失忆又把话重问一遍。
- **历史列表只能看和删，不能点开看内容**，同样是缺那个接口。要支持「点开某条历史会话继续聊」
  或在界面上回看，得先加接口——属独立改动。
  删除**当前正在用的那条会话**时，界面会顺手换一个新 id：否则下一条消息会把刚删的 id 又建回来。
- **测试配置踩了一个坑：自动导入会顺带注入 element-plus 的样式副作用导入。**
  那条链路最终 `import 'element-plus/theme-chalk/base.css'`，而 node 的 ESM 加载器不认 `.css`，
  直接报 `Unknown file extension ".css"`。已在 vite.config.ts 的 test 里把 element-plus
  交给 vite 处理（`server.deps.inline`），CSS 会被 stub 掉，测试耗时没有明显变化。

**正文格式**（追加写，一个会话一段）：

```
## conv=8f3c4d21 | 2026-10-12 14:32 | 12 条
user: 电池低温报警该怎么处理？
assistant: 电池低温告警的核心是……
```

**原子性**：追加直接 append；**物理删除要重写整文件** → 写 `*.tmp` 再 `Files.move(ATOMIC_MOVE)`。
滚动与删除只有这两种走重写路径。

## 5. 关键设计决策

| 决策点 | 备选 | 结论 | 理由 |
|---|---|---|---|
| 索引放在哪 | ① 全局一份 `<root>/memory.md` ② **每用户一份** | **②** | 全局索引随用户数单调增长，且启动要读全量索引。按用户隔离后，**启动读 0 个文件**（比 AC-11 的要求更严格），且天然隔离，不存在跨用户越权读索引 |
| 过期落盘的触发 | ① 定时扫描 ② **Caffeine `removalListener`** | **②** | 无需自写扫描线程；`expireAfterAccess` 直接表达「空闲 30 分钟」 |
| 落盘失败怎么办 | ① 阻塞淘汰 ② **丢弃 + 重试队列** | **②** | 阻塞淘汰会让内存无界增长（更糟）。失败进**有界**重试队列，定时重试；队列满则丢弃并告警——**极端情况下会丢，如实记录** |
| 内存会话超上限 | ① 无上限 ② 部分截断 ③ **整体落盘并驱逐** | **③** | 截断会丢中间内容（与「不丢信息」冲突）；整体驱逐后下次访问从长期记忆**懒加载**回来，无中间状态。避免增量落盘的复杂度 |
| 长期记忆注入 | ① 不排除当前会话 ② **排除当前会话** | **②** | 当前会话已在会话内上下文里，再注入一遍是重复占预算 |
| 同会话并发 | ① 允许交错 ② **串行 + 排队** | **②** | 同一用户同一会话的并发基本是误操作；交错会让上下文顺序错乱。代价：流式期间锁被占用，第二条需等待，故设**等待超时** |
| 审计存哪 | ① 日志 ② 数据库 ③ **独立审计文件** | **③** | `drone-agent` 无数据库；日志会随滚动丢失。独立 append-only 文件可查、可长期保留、不依赖外部 |
| 脱敏在何时做 | ① 写入会话时 ② **落盘时** | **②** | 会话内（内存）保留原文，模型侧需要完整语义；只有落盘的持久副本需要脱敏。**这同时满足 AC-18 与 AC-19** |
| 契约兼容 | ① 保留 `messages` 兼容 ② **直接移除** | **②** | 见第 3 节 |
| 归档跑在哪个线程 | ① 用缓存默认（`ForkJoinPool.commonPool`） ② **显式给专用执行器** | **②** | **实测**：移除回调跑在 `commonPool-worker-*` 上，且是**异步**的（调用方方法返回时尚未触发）。在 JVM 共享池里做文件 IO 会拖累整个进程，且并发度不可控。改为归档一律走调用方提供的执行器（T-3 已落地） |
| 停机刷盘放哪个类 | ① 并进 `MemoryArchiver` ② **拆成 `MemoryShutdownFlusher`** | **②** | 刷盘要读 `SessionStore` 才知道内存里有哪些会话，而 `SessionStore` 构造时又需要一个 `SessionArchiver`——**构造函数互相依赖**，Spring Boot 默认禁止循环引用，会直接启动失败。拆开后由刷盘那个类同时持有两者，依赖方向变单向（T-6 落地） |

## 6. 脱敏规则

落盘前**按顺序**替换。顺序受两条约束，违反任一条都会导致「局部先被改掉、外层规则随之失配」：

1. **外层结构优先**：邮箱、令牌、密码的值里可能含数字；若先跑数字规则，
   邮箱会被切成 `user138****8000@example.com` 这种残缺形态，后续邮箱规则再也匹配不上。
2. **长数字模式优先**：身份证（18 位）先于银行卡（16–19 位）先于手机号（11 位）。

| 顺序 | 类别 | 模式 | 替换 |
|---|---|---|---|
| 1 | 令牌 `sk-` | `sk-` + 8 位以上 | 保留 `sk-`，值 `***` |
| 2 | 令牌 `Bearer` | `Bearer` 后的串 | 保留 `Bearer`，值 `***` |
| 3 | 密码类 | `密码`/`password` + 分隔符 + 值 | 保留标签与分隔符，值 `***` |
| 4 | 邮箱 | 常规邮箱模式 | 首字符 + `***@域名` |
| 5 | 身份证 | 17 位数字 + 数字/X | 保留前 6 后 4 |
| 6 | 银行卡 | 16–19 位数字 | 保留后 4 |
| 7 | 手机号 | `1[3-9]` 开头 11 位 | 保留前 3 后 4 |

> **修订记录（2026-10-13，T-2 实现时）**：原顺序为「身份证 → 银行卡 → 手机号 → 邮箱 → 密钥 → 密码」，
> 只考虑了「长数字优先」，漏了「外层结构优先」。按原顺序，
> `user13800138000@example.com` 会先被手机号规则咬一口，邮箱结构被破坏。已按上表调整。

要求：**不可逆**（遮掉的位数不足以还原原值），且**只动匹配到的片段**，
其余字符逐字保留（AC-19 验证）。

**实现细节（T-2 已落地）**

- 每条数字规则都带 `(?<!\d)` / `(?!\d)` 边界，避免在更长数字串中间咬下一截
  ——否则 19 位数字会被身份证规则咬掉 18 位、剩一位裸露在外。
- 保留结构性标签（`sk-`、`Bearer`、`密码：`）而非整段替换为 `***`：
  读记忆文件的人需要看懂「这里原本是什么」，但不需要看到值。

**已知误报与缺口（如实记录）**

- 16 位以上的**纯数字业务编号**（如某些设备序列号）会被当成银行卡遮掉。
  规则层面无法区分「长得像卡号」与「真的是卡号」，此处选择宁可多遮；若影响使用需单独加豁免。
- **15 位的老式身份证号不在覆盖内**（本规则集按 18 位设计），会被漏遮。
  需要覆盖时须单独加规则。

## 7. 上下文组装与预算

一次对话注入模型的内容 = **会话内上下文** + **长期记忆**：

| 部分 | 来源 | 预算 |
|---|---|---|
| 系统提示词 | 配置（`agent.deepseek.system-prompt`） | 不变 |
| 会话内上下文 | 内存会话的最近 N 条 | **最近 20 条**（沿用 `REQ-AGENT-0002`） |
| 长期记忆 | 该用户历史会话（**排除当前会话**） | **最近 10 轮 / 8000 字符**，超出从最早处截断 |
| 消息角色白名单 | 仅 `user` / `assistant` | 不变 |

## 9. 风险与回滚

| 风险 | 触发 | 影响 | 应对 |
|---|---|---|---|
| 落盘失败致数据丢失 | 磁盘满、权限错 | 过期会话内容永久丢失 | 有界重试队列 + 告警；**承认极端情况会丢** |
| 订阅 `removalListener` 时误把**删除**当**过期** | 显式删除也触发 listener | 刚删的内容被写回长期记忆 | **必须按 `RemovalCause` 分支**：仅 `EXPIRED`/`SIZE` 落盘；`EXPLICIT`/`REPLACED` 不落盘 |
| **淘汰与落盘之间存在时间窗** | 进程在会话被淘汰之后、归档任务执行之前终止 | 该会话内容永久丢失 | 这是**异步归档的固有代价**。缓解：归档执行器单线程、停机时 `cleanUp()` 后等待排空。规格 AC-4 已据此**修订为「异步归档 + 失败进重试队列」**（2026-10-13 批准） |
| 归档回调线程上没有请求上下文 | 实现里若用了 ThreadLocal（如 `UserContext`） | 取到 null，静默出错 | 归档实现**不得依赖 ThreadLocal**；已写进 `SessionArchiver` 的契约 |
| 同会话并发阻塞 | 用户连发 | 第二条等待，超时后失败 | 等待超时 + 明确错误码 |
| 磁盘无监控（遗留） | — | 增长失控无人知 | 已登记为遗留，**上线前必须补告警阈值** |
| 单实例 | 部署两个实例 | 记忆分裂、互相覆盖 | ADR-0003 已明确放弃；部署文档须写明「只允许 1 个实例」 |

### 修订记录

**2026-10-13（T-3 实现时，实测发现）**

1. **移除回调是异步的，且默认跑在 `ForkJoinPool.commonPool` 上。**
   原方案默认按「回调在调用方线程同步执行」设计，实测不成立：
   调用方为 `main` 时回调跑在 `commonPool-worker-1`，且 `cleanUp()` 返回时尚未触发。
   已改为**显式指定专用执行器**（见第 5 节新增决策行），并据此重写测试的等待方式。
2. **单会话消息超上限的路径也改为异步提交**（原写法是同步调用归档）。
   否则同一个归档出口存在两种执行上下文，实现方难以兼顾。
3. **AC-4 的「淘汰前已落盘成功」无法保证**，已修订规格措辞为
   「淘汰后会被异步归档；归档失败进入重试队列」（2026-10-13 **批准**）。

- **上线方式**：一次性（无开关）。契约破坏性变更，前后端必须**同时**上线。
- **回滚步骤**：前后端同时回退到 `REQ-AGENT-0002` 的 `messages` 契约。
  **长期记忆文件保留不删**，回滚后仅不再写入，不阻碍回滚。
- **回滚后数据修复**：无（不涉及数据库）。
