# SDD 开发规范总纲

> Spec-Driven Development（规范驱动开发）。本文件定义**流程**与**门禁**；
> 编码细则：【Java】见 [`java-standards.md`](./java-standards.md)，
> 【前端】见 [`frontend-standards.md`](./frontend-standards.md)；
> 各阶段要填的表格见 [`templates/`](./templates/)。

## 1. 目的与适用范围

**解决什么问题**：把「需求口述 → 直接让 AI 编码」改成「需求 → 规范 → 编码」，
让规范成为**单一真相源**，使评审有依据、变更可追溯、责任可定位。

**适用范围**：【强制】所有新建项目、所有新功能与行为变更。
存量项目不要求推倒重来，但**每一次改动都要按本流程走**，规范随改动逐步补齐。

**不适用**：修错别字、格式化、纯依赖版本升级这类不改变外部行为的改动。

## 2. 核心原则

以下四条不可违背，与下文任何细则冲突时以本节为准。

1. **【强制】规范先于代码。** 先改规范、评审通过，再写代码。不允许「先写完代码再补规范」。
2. **【强制】规范与代码同库、同版本、同提交粒度。** 规范不在外部文档系统里单飞；
   代码回滚时规范一起回滚。
3. **【强制】每条需求可验收。** 需求必须写成能判断真假的形式（见 `templates/spec.md`），
   「性能好」「尽量兼容」这类无法验收的表述不得作为需求。
4. **【强制】需求可追溯。** 每条需求有唯一 ID；实现它的代码、测试、提交信息都要引用该 ID。

## 3. 产物与目录约定

【强制】规范文件放在仓库内的 `docs/sdd/`，与代码同一分支、同一版本：

```
docs/sdd/
├── README.md              # 本文件：流程与门禁
├── java-standards.md      # Java 项目开发规范
├── frontend-standards.md  # 前端开发规范（TS / Vue）
├── constitution.md        # 项目宪法（每个项目一份，长期稳定）
├── specs/
│   └── <需求ID>-<短名>.md  # 一份规格 = 一个可独立验收的变更单元
├── plans/
│   └── <需求ID>-<短名>.md  # 与 specs 一一对应
├── tasks/
│   └── <需求ID>-<短名>.md  # 与 plans 一一对应
├── decisions/             # ADR：架构决策记录，一决策一文件
│   └── ADR-0001-<短名>.md
└── templates/             # 模板，不要改模板的章节结构
```

- **需求 ID 格式**：【强制】`REQ-<模块>-<四位序号>`，例如 `REQ-TASK-0012`。
- 【强制】`specs` / `plans` / `tasks` 三份文件的文件名前缀必须是同一个需求 ID，
  便于用 `grep` 做追溯，不依赖任何工具。

## 4. 流程：五个阶段

每个阶段都有**出口标准**。不满足出口标准，不得进入下一阶段。

### S0 立项与项目宪法

| 项 | 内容 |
|---|---|
| 输入 | 业务目标、约束（预算/期限/合规） |
| 产出 | `constitution.md` |
| 谁写 | 技术负责人 |
| 谁审 | 团队评审后冻结 |
| 出口标准 | 宪法条目全部**可检查**（能被脚本或评审人明确判定真/假），无「尽量」「原则上」这类措辞 |

项目宪法只写**长期稳定、跨需求生效**的约束（技术栈与版本、分层与依赖方向、
统一响应体、安全红线、测试门槛）。它**不是**需求清单，不写具体功能。

### S1 规格（Specify）

| 项 | 内容 |
|---|---|
| 输入 | 需求方口述/文档 |
| 产出 | `specs/<需求ID>-<短名>.md` |
| 谁写 | 需求提出人 + 开发 |
| 谁审 | 领域负责人 |
| 出口标准 | 每条需求有 ID、有验收条件；无技术实现细节（那属于 S3）；范围外事项显式列出 |

【强制】规格只回答**做什么、达到什么效果**，不写「用 Redis 缓存」这类实现选择。
实现选择留给 S3，否则评审时两件事混在一起，谁也说不清在争什么。

### S2 澄清（Clarify）

| 项 | 内容 |
|---|---|
| 输入 | 规格初稿 |
| 产出 | 规格定稿（把待定项一条条关掉） |
| 谁写 | 开发提问，需求方回答 |
| 出口标准 | 规格里**没有未决项**；仍未定的必须写明「不做什么」并记录原因 |

【强制】不确定的地方**问，不要猜**。规格里每留一个「大概是这样」，
后面就是一次返工。澄清结论要回写进规格，不能只留在聊天记录里。

### S3 技术方案（Plan）

| 项 | 内容 |
|---|---|
| 输入 | 规格定稿 |
| 产出 | `plans/<需求ID>-<短名>.md` |
| 谁写 | 开发 |
| 谁审 | 技术负责人（涉及数据模型/接口契约变更时必须有评审记录） |
| 出口标准 | 影响面完整（接口/数据模型/兼容性/性能）；有回滚方案；有测试策略；与 `constitution.md` 无冲突 |

【强制】方案里出现**数据模型变更或接口契约变更**时，必须给出兼容性结论
（不兼容改动要有迁移步骤与回滚方案）。

### S4 任务拆解（Tasks）

| 项 | 内容 |
|---|---|
| 输入 | 技术方案 |
| 产出 | `tasks/<需求ID>-<短名>.md` |
| 谁写 | 开发 |
| 出口标准 | 每个任务**可在一次提交内完成**、有明确完成标志、标注依赖顺序；任务粒度到「改哪个模块的什么职责」 |

【强制】任务不得写成「完成后端」这种体量。一条任务如果预估超过一天，继续拆。

### S5 实现与验收（Implement & Verify）

| 项 | 内容 |
|---|---|
| 输入 | 任务清单 |
| 产出 | 代码 + 测试 + 更新的规范 |
| 出口标准 | 全部验收条件有对应测试且通过；静态检查（lint/格式）零失败；规范与实现一致 |

【强制】实现过程若发现规格或方案有问题，**回到 S1/S3 改规范**，评审后再继续。
禁止「代码里先这么写，规范回头补」。

## 5. 门禁（Gate）

【强制】以下时点必须检查，未通过不得继续：

| 门禁 | 时点 | 检查内容 |
|---|---|---|
| G1 | 进入编码前 | 规格无未决项；方案已评审；任务已拆解 |
| G2 | 提交前 | 提交信息引用需求 ID；测试通过；无硬编码密钥 |
| G3 | 合并前 | 验收条件逐条对应到测试；规范文件与代码在同一提交 |

【强制】规范与代码不一致时，**以规范为准，先改代码或先改规范并说明**，
不允许让两者长期处于不一致状态。发现不一致必须当场修掉。

## 6. 规范变更管理

【强制】改规范本身也要走流程，且比改代码更慎重：

1. 提变更请求（说明动机与影响面）；
2. 改规范文件；
3. 评审；
4. 再改代码。

【强制】规范变更必须在提交信息里单独说明，不能混在功能提交里悄悄改。

## 7. 需求可追溯

【强制】三处必须能追到需求 ID：

- 规格文件标题与文件名；
- 提交信息（格式见 `java-standards.md` 第 12 节）；
- 验收测试的类名或方法名。

【推荐】在 `plans/` 里维护一张「需求 ID → 代码位置 → 测试位置」的映射表。
不用工具也能靠 ID 全文检索定位，这是故意的：工具会换，`grep` 不会。

## 8. 反模式

以下做法**不算** SDD，出现即视为流程未执行：

- 先写代码，事后补一份与实际不符的规范；
- 规范里全是「尽量」「合理」「适当」这类无法判定的词；
- 规范与代码分离在两个仓库/两个系统，版本对不上；
- 规格里直接写实现方案，导致评审时需求与方案无法分开讨论；
- 需求没有 ID，出了问题时说不清是哪条需求引入的；
- 门禁形同虚设——「这次先跳过，下次补」。

## 9. 与 AI 协作的约定

【强制】用 AI（Qoder 等）实现时：

- 每个会话开始，AI 必须**先读** `constitution.md`、当前需求的 `specs/`、`plans/`、`tasks/` 三份文件，再动手；
- AI **一次只做一个任务**，不擅自扩大范围；发现规格缺失就**停下来问**，不许自行假设后继续；
- AI 不得修改 `constitution.md`；不得改 `templates/` 的章节结构；
- AI 产出的代码必须符合 `java-standards.md`，评审时按该文件逐条对照。

仓库根的 `AGENTS.md` 里已声明上述约定，使 AI 在每次会话自动加载。
