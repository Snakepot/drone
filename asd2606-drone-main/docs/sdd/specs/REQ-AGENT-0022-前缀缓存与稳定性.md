# 规格 — REQ-AGENT-0022 前缀缓存与稳定性

- **需求 ID**：`REQ-AGENT-0022`
- **提出人 / 日期**：需求方 / 2026-10-23
- **负责人**：AI（按 SDD 执行）
- **前置**：`REQ-AGENT-0017`（账单，含缓存命中数）、`REQ-AGENT-0018`（工具裁剪）、`REQ-AGENT-0021`（停注入）

## 1. 背景与目标

DeepSeek 对**相同前缀**自动做上下文缓存，返回 `prompt_cache_hit_tokens`。
真机观测：同一会话第二轮命中 **98.3%**，重启后同配置首轮仍命中 **98.6%**。
但「命中」依赖前缀逐 token 相同，而我们的前缀由三部分拼成：

1. 系统提示词（含按权限裁剪的 Skill L1）；
2. 工具定义（本地 + MCP，受角色/权限裁剪）；
3. 消息（会话 + 摘要）。

其中 1、2 是固定成本的大头（约 12.6k token 中的 12.6k），**只要顺序抖动，
整段缓存就失效**。当前 MCP 工具顺序来自服务端 `tools/list` 返回顺序，没有保证。

目标：**让同一套配置在任何一次启动、任何一次请求里产出同一个前缀**，并把
「前缀指纹 + 缓存命中率」打进账单，便于判断命中/未命中的原因。

## 2. 范围

### 做（In Scope）

- MCP 工具按暴露名排序后再注册（行为与元数据同步重排）；
- 请求构造时计算**前缀指纹**（系统提示词 + 工具定义的 SHA-256 前 12 位）；
- 账单日志增加：前缀指纹、缓存命中率（%）；
- 单元测试保证：同输入同指纹、追加消息不改前缀、权限变化指纹变化（预期）。

### 不做（Out of Scope）

- 不做缓存 TTL/预热/保活（供应商控制，API 未暴露）；
- 不追求跨 API Key 的缓存共享（供应商行为）；
- 不改系统提示词的分节顺序（`{{skills}}` 位置不动，避免行为回归）；
- 不把消息部分纳入指纹（消息是后缀，变化是正常的）。

## 3. 验收条件

| 编号 | 前置 | 操作 | 预期 |
|---|---|---|---|
| AC-1 | 同一进程、同一用户 | 连续发两条 | 两次账单的指纹**相同**；第二条命中率显著高于第一条 |
| AC-2 | 重启服务、配置不变 | 再发一条 | 指纹与重启前**相同**；命中率仍有较高值 |
| AC-3 | 同一会话 | 追加一条消息 | 指纹不变（消息是后缀，不应影响系统+工具前缀） |
| AC-4 | 不同角色/权限 | 各发一条 | 指纹**不同**（Skill L1 与工具集不同，属于预期） |
| AC-5 | 每次模型调用 | 看账单 | 日志含 `前缀指纹=…` 与 `缓存命中=X（Y%）` |

### 非功能要求

- 指纹计算为一次 SHA-256（约 30KB 输入），单次 < 1ms；
- 排序不改变工具集合，只改变下发顺序；
- 日志不包含前缀正文。

## 4. 约束与依赖

- 前缀是否命中由供应商决定；本需求只保证「我们发出去的字节稳定」，不承诺命中率；
- 缓存可能因供应商 TTL、账号策略失效，无法从本服务侧控制；
- 会话压缩（REQ-0020）会在摘要生成时**一次性**改变消息前缀，属于预期事件。
