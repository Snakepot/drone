# 规格 — REQ-AGENT-0027 写工具幂等（MCP 转发层）

- **需求 ID**：`REQ-AGENT-0027`
- **提出人 / 日期**：需求方 / 2026-10-26
- **负责人**：AI（按 SDD 执行）
- **前置**：`REQ-AGENT-0026`（traceId 透传）、`REQ-AGENT-0007`（失败重试）

## 1. 背景与目标

编排层允许「工具失败后由模型再试」。问题出在**写操作**：

- 上游已经执行成功，但响应超时/网络中断，agent 收到失败；
- 模型按重试预算再发一次同样的调用 → **重复派发、重复处置、重复删除**。

目标：对**写工具**做幂等保护——同一 trace、同一用户、同一工具、同一参数，
在短时间内只真正执行一次；超时导致的「结果未知」明确告知模型先去查询确认，不要盲目重试。

## 2. 范围

### 做（In Scope）

- 在 `drone-mcp-server` 的 `ToolInvoker` 层加幂等：
  - 仅对 `ToolSpec.readOnly() == false`（POST/PUT/DELETE 等）生效；
  - 幂等键 = `traceId + userId + 工具名 + 参数规范化哈希`；
  - 成功结果缓存 **10 分钟**；
  - 超时 / 5xx / 网络异常 → 记录「结果未知」缓存，重试时**不再执行**，返回
    「请先用查询工具确认状态」；
  - 并发重复请求：同一键只允许一个执行，其余等待并复用结果；
  - 读工具不缓存（数量大、重复读无害）。
- 日志：命中、执行、结果未知三类事件可区分。

### 不做（Out of Scope）

- 不做跨实例共享（缓存是进程内；多实例时由网关/DB 幂等承接）；
- 不改 `drone-server` 的业务接口（它仍然没有幂等键）；
- 不改 agent 编排的重试策略（仍由模型决定是否重试）；
- 不做人民币/配额（属于 P0 的另一项）。

## 3. 验收条件

| 编号 | 前置 | 操作 | 预期 |
|---|---|---|---|
| AC-1 | 写工具、同一 trace | 相同参数调用两次 | 上游只被调用一次；第二次返回与第一次相同结果 |
| AC-2 | 写工具、第一次上游超时 | 重试相同参数 | 上游**不再调用**；返回「结果未知，请先查询确认」 |
| AC-3 | 读工具、同一 trace | 相同参数调用两次 | 上游调用两次（不缓存） |
| AC-4 | 写工具、不同 trace | 相同参数各调一次 | 上游调用两次（不同请求不得互相吞掉） |
| AC-5 | 参数只差顺序 | 同一 trace 两次 | 视为同一操作（规范化后哈希一致） |
| AC-6 | 未带 Authorization | 调用 | 与现状一致：直接拒绝，不进入幂等逻辑 |
| AC-7 | 缓存超过上限 / TTL 到期 | 调用 | 旧条目被清理，不无限增长 |

### 非功能要求

- 幂等缓存不存储 Token、Authorization 原文；键里只放用户 id 的派生值；
- 缓存命中也要打 INFO，便于判断「没执行」不是「丢日志」；
- 缓存写失败/清理失败不影响工具调用（纯内存，无 IO）。

## 4. 约束与依赖

- 依赖 agent 透传 `X-Trace-Id`（REQ-AGENT-0026，当前工作区未提交）；
- 同一 trace 内**合法的重复写**（用户明确要求「再派一次」）会被吞掉——这是刻意取舍，
  真要重复执行应由用户发起新请求（新 trace）；
- 进程重启后缓存丢失；已知限制，后续迁 Redis/DB。
