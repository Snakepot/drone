# 规格 — REQ-AGENT-0017 上下文账单（按消息计量）

- **需求 ID**：`REQ-AGENT-0017`
- **提出人 / 日期**：需求方 / 2026-10-23
- **负责人**：AI（按 SDD 执行）
- **前置**：`REQ-AGENT-0016`（流式与思考展示）

## 1. 背景与目标

实测一次普通请求的 body 为 33.6k 字符，其中**工具定义占 29.6k（88%）**；而现有预算
（`max-result-chars`、`inject-max-chars`）全是**字符**口径，无法回答三个问题：

1. 这次请求到底花了多少上下文预算？
2. 花在系统提示词、长期记忆、会话、工具结果、工具定义上的比例是多少？
3. 估算和模型真实计费差多少？

目标：**把每条发给模型的消息封装成带计量信息的对象**，每次模型调用输出一份按类别
汇总的「上下文账单」，并用模型返回的 `usage` 对账。

## 2. 范围

### 做（In Scope）

- 新增消息包装对象：消息本体 + 类别（系统 / 长期记忆 / 会话 / 工具调用 / 工具结果 / 续跑）
  + 工具名 + 估算 token。
- 新增 token 估算器（按 DeepSeek 实测系数：中文 0.62/字、其他 0.22/字符、每条消息 4、模板 22）。
- 每次模型调用（`chat` / `chatStep` / `streamChat` / `streamStep`）输出一条 INFO 账单日志。
- 流式请求开启 `stream_options.include_usage`，账单里带上真实 `prompt_tokens` 与缓存命中数。
- 工具定义作为账单的独立一行（不属于消息，但同属请求上下文）。

### 不做（Out of Scope）

- **不改现有字符预算的拦截行为**（压缩 / 截断 / 轮次上限保持原样）；
- 不引入第三方 tokenizer（DeepSeek 无公开 tokenizer；用实测系数估算）；
- 账单不落库、不上前端，只进日志；
- 不做基于 token 的自动压缩（需要先有账单数据，后续需求）。

## 3. 验收条件

| 编号 | 前置 | 操作 | 预期 |
|---|---|---|---|
| AC-1 | 任意一次带工具的对话 | 查看日志 | 每次模型调用都有且仅有一条 `【上下文账单】`，含 traceId 与合计 |
| AC-2 | 同上 | 看账单分类 | 系统提示词 / 长期记忆 / 会话 / 工具调用 / 工具结果 / 工具定义 分别给出 token 与条数 |
| AC-3 | 工具结果回填 | 看账单 | 工具结果条目带**工具名** |
| AC-4 | 流式对话 | 看账单 | 出现 `实际 prompt_tokens` 与 `缓存命中`，并给出估算偏差百分比 |
| AC-5 | 固定文本样本 | 单测估算 | 中文/英文/混合文本的估算值与实测系数一致（误差 ≤ 1 token/100 字符） |
| AC-6 | 未配置 API-KEY（离线单测） | 构造消息并计算账单 | 不发起网络请求，账单可独立计算 |

### 非功能要求

- 账单计算为**纯内存**操作，单次耗时 < 1ms；
- 日志不得包含消息正文（只给数量与 token），避免把用户数据写进常规日志。

## 4. 约束与依赖

- 估算系数来自 2026-10-23 对 `deepseek-flash` 的实测：
  112 汉字 → 73 token；132 ASCII → 32 token；每条消息约 4 token；固定模板约 22 token。
- 系数会随模型/分词器变化，因此账单必须同时打印**实际值**用于校准。
