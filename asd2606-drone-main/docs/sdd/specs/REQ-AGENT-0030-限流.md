# 规格 — REQ-AGENT-0030 请求限流（每用户 + 全局）

- **需求 ID**：`REQ-AGENT-0030`
- **提出人 / 日期**：需求方 / 2026-10-26
- **负责人**：AI（按 SDD 执行）
- **前置**：`REQ-AGENT-0028`（预算执行）

## 1. 背景与目标

预算能按 token 拦住「总量」，但挡不住**短时突发**：

- 同一用户可并发开多个会话，把共享 API Key 打满；
- 单个会话虽然串行，但多会话并发没有上限；
- 预算按天结算，突发请求可能在额度内就把延迟打高。

> 限流的算法与取舍（令牌桶 / 漏桶 / 滑动窗口 / 并发信号量）见
> `plans/REQ-AGENT-0030-限流.md` §1。

目标：在 `/chat` 与 `/chat/stream` 入口加**每用户 + 全局**两道限流：

1. **QPS**：令牌桶，限制每秒新增请求；
2. **并发**：限制同时处理的请求数；
3. 超限快速拒绝，不调模型、不占会话锁。

## 2. 范围

### 做（In Scope）

- 每用户 QPS（burst 可配）与并发上限；
- 全局 QPS 与并发上限；
- `/chat`、`/chat/stream` 入口检查；
- 超限返回明确话术；流式通过 `error` 事件返回；
- 配置开关与回滚；
- 日志：拒绝原因、userId、当前并发。

### 不做（Out of Scope）

- 不做分布式限流（单实例内存）；
- 不做按接口/按工具细粒度限流；
- 不做排队等待（直接拒绝，避免请求堆积）；
- 不改预算逻辑。

## 3. 验收条件

| 编号 | 前置 | 操作 | 预期 |
|---|---|---|---|
| AC-1 | 用户 QPS/burst 已用尽 | 再发请求 | 不调模型；返回「请求过于频繁」 |
| AC-2 | 用户并发已满 | 再发请求 | 不调模型；返回并发限制提示 |
| AC-3 | 全局并发已满 | 任意用户请求 | 拒绝；不影响已处理请求 |
| AC-4 | 超限的流式请求 | 请求 `/chat/stream` | 收到 `error` 事件并结束，不进入编排 |
| AC-5 | 令牌桶随时间恢复 | 等待后重试 | 请求成功 |
| AC-6 | `enabled=false` | 超限场景 | 不拦截（回滚） |
| AC-7 | 正常请求 | 完成/断开 | 并发计数正确释放，不泄漏 |

### 非功能要求

- 检查为纯内存，单次 < 1ms；
- 拒绝时不写会话、不产生模型费用；
- 释放并发必须幂等（完成/异常/超时任一触发只减一次）。

## 4. 约束与依赖

- 单实例内存限流；多实例需 Redis/网关限流；
- 默认值：用户 2 QPS / burst 4 / 并发 2；全局 20 QPS / burst 40 / 并发 20；
- 流式请求的并发在 emitter 完成/异常/超时时释放。
