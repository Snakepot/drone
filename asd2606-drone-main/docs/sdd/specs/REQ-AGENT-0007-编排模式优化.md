## 1. 背景与目标

现行编排是最**基础**的 ReAct 循环：单 agent、一个硬性的「轮数上限」、无反思、工具结果**只做纯截断**。
工具变多、任务变长之后，三处短板会显现：

1. **失败不会自愈**：工具一旦超时/报错，就回填一句「查不到」收场，**不会换种方式再试**。
2. **结果利用不经济**：回填**只按长度一刀切截断**，尾部信息直接丢；该省的地方不省、该留的地方没留。
3. **预算只有一维**：只有「轮数」这一个刹车，**没有对「步数 / 回填长度 / 结果总量」的显式预算**，
   长任务要么过早收场，要么失控变贵。

目标：让编排在本需求范围内**更稳（失败能自愈）、更省（token 花在刀刃上）、更可控（预算显式、有序收尾）**。
这是「基础 ReAct → 进阶」的演进，**不改变** ReAct 的因果骨架（跨轮仍串行）。

## 2. 范围

### 做（In Scope）

- **受控重试（Reflexion-lite）**：某次工具调用**失败**时，编排**不立即收场**，而是在预算内把失败信息
  交回模型，让它决定「换参数重试 / 换工具 / 如实告知」；重试有**次数上限**，达上限即有序收尾
- **工具结果的中间压缩**：工具回填内容超过阈值时，**先压缩再回填**，替代「纯截断」；
  压缩方式见 Q-2
- **显式预算**：把「轮数上限」扩展为 **步数 + 单次回填长度 + 工具结果总量** 三个预算；
  超预算时**有序收尾**（返回已有内容并说明），**不是**直接报错
- **可观测**：日志（及必要时响应）能读出「用了几步、重试了几次、压缩了几次」

### 不做（Out of Scope）

- **不做 Plan-and-Execute**（先出计划再逐步执行）：体量大、依赖稳定的工具集，**本期不做，以后再说**（Q-5）
- **不做多 agent 协作 / 角色分工**
- **不做跨轮并行**（ReAct 的因果顺序不可并行；同轮并行属 `REQ-AGENT-0005`）
- **不引入外部向量记忆 / RAG**
- **不改 `/chat` 的入参出参**（除非实现时发现必须，再回规格议）

## 3. 验收条件

| 编号 | 前置（Given） | 操作（When） | 预期（Then） |
|---|---|---|---|
| AC-1 | 某工具调用**失败**（超时/异常/无结果） | 编排继续 | **不立即收场**：在预算内把失败信息交回模型再决断；若模型选择重试且成功，用户拿到**基于成功结果**的答复 |
| AC-2 | 连续重试达到**上限** | 再失败 | **有序收尾**，返回「已尽力」类答复；**不无限重试** |
| AC-3 | 工具结果**超过阈值** | 回填 | 回填的是**压缩后**内容（长度 ≤ 阈值），且最终答复仍能引用其中**要点** |
| AC-4 | 达到**步数 / 长度**预算 | 继续 | **有序收尾**（返回已有内容并说明），**不是** 500 |
| AC-5 | 一次含重试与压缩的 `/chat` | 查看日志 | 日志可读出**步数 / 重试次数 / 压缩次数** |
| AC-6 | 关闭优化开关（配置） | 使用助手 | 行为与**现状一致**（可回退） |
| AC-7 | 任一调用 | 查看日志 | **不含** API Key / `Authorization`（沿用既有红线） |

### 非功能要求

- 性能 / 成本：同一问题下，**回填 token 相对现状下降**；重试只在失败时发生（不常态化加价）
- 容量：本期不做要求
- 安全：日志脱敏红线不变；工具是否有副作用仍由 `REQ-AGENT-0006` 治理
- 兼容：`/chat` 契约不变；`agent.tool.enabled=false` 仍回到纯对话

## 4. 约束与依赖

- 依赖 `ToolCallingService` 的既有循环；本需求改的是**循环内部的策略**，不改 ReAct 骨架
- 与 `REQ-AGENT-0005` 有交叠：预算与耗时日志**共用**同一套配置与日志口径，两边需对齐
- 中间压缩若采用「模型摘要」，会**多一次模型调用**（成本↑、延迟↑），是 Q-2 的核心取舍
