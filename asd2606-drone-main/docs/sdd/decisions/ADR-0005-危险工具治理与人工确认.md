# ADR-0005 危险工具引入「权限码 + 人工二次确认」，服务端为此新增短期有状态

- **状态**：提议（待评审）
- **日期**：2026-10-14
- **决策人**：项目负责人（待确认）
- **记录人**：AI（按规范登记）
- **关联**：[ADR-0003](./ADR-0003-引入记忆与服务端有状态.md)、[`specs/REQ-AGENT-0006-危险工具治理.md`](../specs/REQ-AGENT-0006-危险工具治理.md)

## 背景

`REQ-AGENT-0004` 让助手能调用工具，且**工具一被模型请求就自动执行**。对只读工具（查天气）没问题；
但后续会出现**不可逆**的工具——删除设备、删除飞手、解散任务、下发指令。

这类工具若沿用「自动执行」，风险有两个：
1. **模型误判**：把用户的闲聊/假设性问题当成执行指令；
2. **越权**：能聊天的人未必有删数据的权限（例如飞手 vs 管理员）。

因此「执行前要有人的明确授权」不是可选体验，是**安全前提**。

## 决策

### 1. 工具有权声明「所需权限码」，执行前在服务端比对

- 复用 `drone-agent` 现成的 RBAC（`AuthoritiesClient` + `UserContext`），**不新建一套权限体系**。
- 权限不足 → **不执行**，回填「无权限」；**绝不提权**。
- 权限判定只在服务端；前端隐藏入口不构成安全边界（与宪法第 4 节一致）。

### 2. 「危险」工具执行前需**人工二次确认**

- 工具可声明为「需确认」；命中时**不立即执行**，先返回「待确认 + 动作摘要」，
  由用户在前端确认后**再执行**。
- 后果：**服务端新增短期有状态**（保存待确认动作）。
  这与 `ADR-0003`「服务端转为有状态、单实例」的前提一致，**不新增多实例诉求**。

### 3. 待确认动作必须有**有效性边界**

- **有效期**（过期即拒）、**幂等**（重复确认只执行一次）、**归属校验**（只能本人确认自己发起的动作）。
- 理由：确认动作本质是「一次授权的票据」，票据必须防重放、防越权、防永久有效。

### 4. 危险工具执行**留审计**

- 记录 who / tool / 参数摘要 / 结果 / when，便于事后追溯（可仿 `MemoryAuditLog` 的形式）。

### 5. 只读工具**不进**确认流程

- 否则每次查天气都要点确认，体验不可接受。**按「有无副作用」分类**，而不是一刀切。

## 后果

- 助手从「自动执行」变成「危险操作需真人授权」，安全性提升、交互多一步。
- 引入**待确认动作**这一份短期状态，需要过期与清理策略；服务仍为单实例。
- 需要 `drone-server` 侧**新增权限码并授给正确的角色**（飞手不得持有删除类权限）。
- 与 `REQ-AGENT-0005` 共用「工具是否有副作用」这份元数据。

## 未决 / 遗留

- 待确认动作的**存储介质与有效期**未定（`REQ-AGENT-0006` 的 Q-1）。
- 「危险」的界定方式（工具自声明 vs 配置清单）未定（Q-2）。
- 权限码清单与角色授予未定（Q-3）。
- 前端确认的接口形态未定（Q-4）。
- **本决策为提议**，经技术负责人评审后方可进入实现。
