# ADR-0004 引入工具调用，天气数据源采用无 Key 的可替换实现

- **状态**：提议（待评审）
- **日期**：2026-10-14
- **决策人**：项目负责人（待确认）
- **记录人**：AI（按规范登记）
- **关联**：[ADR-0003](./ADR-0003-引入记忆与服务端有状态.md)、[`specs/REQ-AGENT-0004-工具调用.md`](../specs/REQ-AGENT-0004-工具调用.md)

## 背景

助手目前无法获取实时信息。用户询问**飞行相关天气**（起飞前必须判断的要素）时，
模型只能编造或答「不知道」。要让助手能查实时信息，必须引入**工具调用**能力。

需求方给出的流程是：定义获取天气的方法（内部联网搜索）→ 定义工具描述（name/desc/param）
→ 把用户问题与工具定义传给模型 → 模型返回要调用的工具 → 调用工具并拿到结果 →
把用户问题与工具结果再传给模型 → 模型返回最终答复。

落地前暴露了三个必须先定、且影响架构的选择。

## 决策

### 1. 天气数据源用**无 Key** 的 Open-Meteo，且抽象为可替换接口

- **Bing 官方搜索 API 已于 2025-08-11 退役**，故最初设想对接 Bing 不成立。
- 曾选「无 Key 的通用搜索 DuckDuckGo Lite」，但 **T-8 实测被其反爬挡住**：
  `lite` / `html` 端点均返回 **HTTP 202 + 首页**，拿不到任何结果 —— 该实现**不可用**。
- 需求方复议后**改定 Open-Meteo**（官方免费接口、**无需 Key**、返回真实 JSON）。
  它**只覆盖天气**、不是通用搜索：这是明确接受的取舍。
- **前提条件**：数据源必须抽象成 `WeatherProvider` 接口。将来换别家（含需 Key 的）
  **只加一个实现类，上层不动**。
- **已知代价（如实登记）**：
  - 只覆盖天气，非通用搜索；
  - 依赖外网可达；内网 / 出网受限时请求失败，**必须降级**为「查不到」而不是让整条请求失败。

### 2. 工具调用只做**非流式** `/chat`

- 流式下工具调用需要「边收流边拼 `tool_calls`、再发起第二轮生成」，复杂度显著更高。
- 本期只做非流式；**流式路径保持现状**，不引入回归风险。

### 3. **复用当前模型**，不单独配置工具模型

- 使用现有的 `deepseek-flash` + 深度思考配置。
- 若该配置**不支持** function calling，则**直接报错**，不静默降级或偷偷换模型——
  「悄悄换模型」会让行为不可预期。
- **未验证项**：当前模型与 thinking 模式对 tools 的兼容性**尚未实测**，
  实测结论若与预期不符，回 `specs/`、`plans/` 与本文档调整。

### 4. 工具调用的中间消息**不写入会话记忆**

- 会话记忆只新增「用户消息 + 最终助手答复」两条。
- 理由：工具请求/结果会污染后续上下文、放大记忆体积，且对后续追问无价值。

### 5. 天气范围限定为**飞行相关**

- system prompt 增补：放行「飞行相关天气」；纯生活化天气仍按现状委婉拒绝。
- 理由：这是对既有「只答无人机业务」边界的**定向扩展**，不是取消边界。

## 后果

- 助手具备工具调用能力，为后续更多工具（如查库存、查任务）留出扩展点。
- 引入了对**第三方非官方接口**的运行时依赖，需在部署文档中登记其局限与降级行为。
- 搜索结果的 token 成本需靠**截断**控制（见方案第 5 节）。

## 未决 / 遗留

- 当前模型对 tools 的支持情况：**T-8 已实测支持**（原为未验证项），此项关闭。
- Open-Meteo 的**可用性已在开发环境实测**（HTTP 200、返回真实 JSON）；
  但**生产 / 部署环境的出网策略未验证**，上线前需确认 `drone-agent` 能访问
  `geocoding-api.open-meteo.com` 与 `api.open-meteo.com`。
