# ADR-0001 存量回填范围：只回填 drone-agent，不回填 drone-server

- **状态**：已接受
- **日期**：2026-10-12
- **决策人**：项目负责人
- **记录人**：AI（按 `../templates/` 与宪法第 8 节要求登记）

## 背景

SDD 规范于 2026-10-12 回填到本仓库。仓库含四个工程（`drone-server`、`drone-agent`、
`drone-web`、`drone-app`），其中 `drone-server` 体量最大、历史最久。

问题：是否要把**历史需求**也逐条回填成 `specs/` / `plans/` / `tasks/` 三件套？

这个决定影响面很大——回填是考古工作，成本随历史体量线性增长，且回填件本身
按规范第 8 节属于反模式（事后补规范），做多了反而稀释规范的严肃性。

## 可选方案

| 方案 | 说明 | 成本 |
|---|---|---|
| A. 全仓库回填 | 四个工程的历史需求全部补齐档案 | 高 |
| B. 只回填 `drone-agent` | 只补 `drone-agent`；`drone-server` 不建档案 | 低 |
| C. 只立规范、不建任何档案 | 保留流程与规范文件，历史需求一律不补 | 最低 |

## 结论

**采纳 B。**

- **`drone-server` 的历史需求不回填**，不为它补 `specs` / `plans` / `tasks`。
- **`drone-agent` 严格按照规范执行**：新需求走完整五阶段流程；
  已有需求（`REQ-AGENT-0001`、`REQ-AGENT-0002`）的验收缺口逐步补齐。

## 后果

**正面**

- 成本可控：不为一个多年累积的大工程做全量考古。
- 流程先在 `drone-agent` 这个边界清晰的小服务上跑通，跑顺了再谈推广。

**负面 / 必须留意的**

- 宪法末尾「当前差距」里的多数条目是 `drone-server` 范围的（覆盖率门槛、CI 门禁、
  分支保护），在 B 方案下**长期不会清零**，会一直挂在表里。这不是遗忘，是已知状态。
- **同一仓库存在两种执行力度**（`drone-agent` 严格、`drone-server` 宽松）。
  团队必须知道这一点，否则容易误以为「整个仓库都在按 SDD 走」。
  这一条应在推广时明确说明，不要让它变成隐含假设。

## 未决事项

- `drone-server` 的**新增改动**是否同样严格按规范执行，**尚未拍板**。
  「不回填」只回答了「要不要补历史档案」，没有回答「新改动怎么走」。
  在拍板之前，`drone-server` 的新改动沿用既有习惯（见 `AGENTS.md` 的 Git 约定）。
