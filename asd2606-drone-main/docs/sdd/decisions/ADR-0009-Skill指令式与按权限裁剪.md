# ADR-0009 Skill 采用「指令式 SOP + 按权限裁剪 L1」，不做工作流引擎

- **状态**：已接受
- **日期**：2026-10-22
- **决策人**：项目负责人
- **记录人**：AI（按规范登记）
- **关联**：[`specs/REQ-AGENT-0014-业务流程Skill.md`](../specs/REQ-AGENT-0014-业务流程Skill.md)

## 背景

要把「运营日报、派发前检查、告警分诊、交接班」这类可固定的流程沉淀成资产，并让不同的用户只看到
自己用得上的流程（省 token）。有两条路：

1. **工作流引擎**：Skill 写成 DSL（步骤、条件、参数映射），由代码解释执行；
2. **指令式 SOP**：Skill 写成 Markdown 步骤，由模型按步骤调用已有工具。

## 决策

### 1. 采用指令式 SOP，不做 DSL 引擎

- Skill 是 `SKILL.md`（frontmatter + 正文），正文用编号步骤写清「调哪个工具、传什么参数、按什么版式输出」。
- 执行仍走既有的工具循环与治理（危险确认、RBAC、审计），**不新增第二套执行器**。
- **代价（如实登记）**：步骤是否被严格遵守取决于模型；无法在代码层强制顺序。
  缓解：`use_skill` 的返回里重复「必须按序、缺一步停下说明」，并在冒烟中逐条核对。
- **不选引擎的理由**：现有工具调用已经能表达顺序、分支与错误处理；引擎要重写参数映射、条件、
  重试与可观测性，收益（确定性）在当前 4 条流程上不足以覆盖复杂度。
  将来若出现「必须逐字执行、不能由模型决定」的流程（如结算），再单独引入引擎。

### 2. L1 元数据按用户权限裁剪

- 每个 Skill 的 frontmatter **必须**声明 `permissions`，用户**全部具备**才可见、可用。
- 系统提示词里的 L1 清单是**按当前请求的用户**实时过滤的，而不是一份全局文本。
- 权限通过 `ToolContext` 显式传入提示词装配层（工具循环、普通对话、SSE 流式三个入口）；
  SSE 在请求线程上取权限后再进异步线程，避免 ThreadLocal 被清理后取不到。
- **不选「全局展示、调用时再拦」**：那会让每个用户都背着所有流程的元数据，违背省 token 的初衷。
- 可见性只是体验优化：**真正的授权边界仍在 `drone-server`**，`use_skill` 也会二次校验，
  无权限与不存在返回同一句文案，避免暴露流程存在性。

### 3. Skill 随包发布

- 放在 `src/main/resources/skills/`，与 prompts 一致：进 git、可评审、可回滚，改文件需重启。
- **不做在线编辑/热加载**：那会引入权限、审计与版本一致性的一整套问题，超出本期。

## 后果

- 正面：新增流程只需加一个目录；L1 成本随可见数量线性增长；执行链路与既有治理完全复用。
- 负面：步骤依赖模型遵守；Skill 与工具可能漂移（用 frontmatter 的 `tools` + 启动校验缓解）。
- 明确**不选**：DSL 工作流引擎、全局 Skill 清单、在线编辑热加载。
